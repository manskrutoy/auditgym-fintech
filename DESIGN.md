# Записка о дизайне AuditGym

## Идея

Чтобы среда была пригодна для RL, каждое расхождение должно быть **истинным фактом о
скрытой истории**, а не случайной подозрительной строкой. Поэтому генерация идёт в три слоя:

```
seed, config ──► World (скрытая история)       клиенты, счета, платежи, курсы, расходы
                    │  чистые решения            дата/время проводки, дата курса, применённые распределения
                    ▼
                Injectors ── одно задокументированное изменение на ошибку (provenance)
                    │
                    ▼
                post_ledger(world) ──► проводки (детерминированно, двойная запись)
                    │
     clean copy ◄───┴───► dirty books ──► render (случайные ID, порядок) ──► public/ + private/
     (мутации отменены)
```

1. **World** (`world.py`) — согласованная история. Все документы правдивы: суммы строк, сроки, ссылки платежей на счета той же валюты, курсы на рабочие дни.
2. **Решения бухгалтера** (`InvPost`, `PayPost`) задают, *как* документы попали в книгу.
3. **Инжекторы** (`injectors.py`) меняют одно решение или добавляют подложный документ и возвращают `PlannedIssue`: тип, затронутые объекты, правило подсчёта суммы и допустимые наборы доказательств.
4. **Проводки** (`posting.py`) строятся одной функцией и для чистой, и для ошибочной версии. Если ошибка влияет на последствия (например, неверный курс по счёту меняет курсовую разницу при оплате), это происходит естественно, без ручной подгонки.

## Гарантии корректности (проверяются при каждой генерации)

- **До ошибок** (`check_clean_invariants`): каждый журнал сбалансирован, каждый документ проведён ровно один раз, в свою дату и по курсу политики; полностью оплаченные счета закрыты в AR; ссылки платежей суммируются в платёж; оплата идёт после счёта; оборотно-сальдовая ведомость сходится.
- **После ошибок**: журналы по-прежнему сбалансированы (ошибки содержательные, а не арифметические). `check_declared_changes` доказывает, что чистая и ошибочная книги различаются **только** на строках объявленных документов и их прямых последствий. Построчный diff сохраняется в `provenance.json`.
- **Эталон** пересчитывается из записанной книги. Сумма > 0, все доказательства публичны (`fx_id` проверяется на публикацию). Если инвариант не выполнен, генерация детерминированно повторяется со следующим номером попытки.
- **Независимая проверка** (`verify.py`) использует только публичные записи. Каждый эталон пересчитывается из каждого допустимого набора доказательств, а независимый детектор по опубликованной политике находит ровно объявленные ошибки: ничего лишнего и ничего недоказуемого.

## Почему трюки не работают

| трюк | что мешает |
|---|---|
| «одинаковый клиент и сумма = дубль» | ежемесячные подписки и одинаковые суммы за разные услуги; дубль отличается только идентичными строками и датой |
| «строка в 1190 = ошибка» | неопознанные поступления законно лежат в 1190; ошибка видна только при сравнении с remittance |
| «напечатанная дата» | документы в поясах ±8–10 ч, граница периода по местному времени компании, курс на выходных берётся с прошлого рабочего дня |
| «пометить всё» | лимит 30 выводов, взаимно однозначное сопоставление, F1 → −1 |
| «угадать ID / убедить текстом» | нужны точное множество ID, сумма, валюта и полный набор доказательств; текст не оценивается |
| порядок и номера ID | ID случайны и не монотонны; совпадения времени разрешаются по случайному ID |

## Награда

Общая функция задачи: `clip(2·F1 − 1 − 0.002·steps, −1, 1)`. Награда по ходу равна нулю,
подсказок о правильности нет. В eval-режиме награда не возвращается политике. Экспериментальная
F0.5-награда показывается отдельно. Шаговый штраф (максимум 0.2) меньше цены одного TP, поэтому
экономия шагов лишь немного различает равные ответы.

Следствие формулы из ТЗ, которое мы сознательно сохраняем: эпизод, обрезанный по лимиту, на
чистых книгах даёт пустой ответ, то есть F1 = 1 и награду около 0.8 (1 − 0.002·100). Пустой ответ
на чистых книгах верен по существу, а штраф за шаги отличает его от быстрого правильного ответа.
На ошибочных книгах тот же исход даёт −1.

## Изоляция

Эту часть проверяла отдельная красная команда агентов; найденные ею пути к эталону закрыты так:
- секрет оценщика `AUDITGYM_SECRET` (HMAC во всех RNG-потоках и в `episode_id`) не даёт подобрать seed по публичным ID и пересоздать эталон;
- ID выдаются в случайном порядке, поэтому поток ID не выдаёт порядок создания документов;
- процесс политики запускается из песочницы только с кодом политик, от `nobody`, без доступа к `private/`;
- час выставления счёта и день платежа у внесённых ошибок берутся из того же распределения, что у обычных документов, а для платежей в последние дни периода добавлены корректные отвлекающие случаи той же формы.

Оценщик хранит truth в своём процессе. Политики работают в отдельных процессах и видят только
наблюдения: копии запрошенных записей. Oracle существует только внутри оценщика. Парные проверки
(повтор, переименование ID с перестановкой, смена id/order seed) входят в `python -m auditgym check`.

## Измеренный разбор сбоев

`auditgym/analysis.py` привязывает каждый ложный вывод базовой политики к ловушке, которая его
вызвала: законно повторяющаяся сумма, напечатанная или UTC-дата вместо местной, курс выходного дня,
граница периода в чужом поясе, законно неприменённое поступление. Каждый пропуск привязывается к
внесённому варианту ошибки из provenance. Результат: `reports/failure_analysis.md`.

## Безвредные преобразования

Парные проверки меняют представление, но не факты: случайное переименование всех ID, перестановку
записей, перевод всех меток времени в случайные UTC-смещения (моменты времени те же), а также
смену `id_seed`/`order_seed` генератора. После каждого преобразования эталон проходит независимую
проверку, oracle получает +1, а F1 эксперта не меняется.

## Ограничения

См. README, раздел 10: только AR, фиксированные смещения поясов, открытый генератор требует
64-битных закрытых seed, награда не доказывает пригодность для реального аудита.
